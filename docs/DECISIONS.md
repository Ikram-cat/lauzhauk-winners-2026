# Architecture decisions

This log records the project baseline as of 21 November 2026. The master plan supplies the product goals and original rationale. Decisions below describe the design to implement. For build, deployment and provider verification, see the handoff. [Master plan](MASTER_PLAN.md) · [Session handoff](SESSION_HANDOFF.md)

| ID | Decision | Rationale | Alternatives considered | Consequences |
| --- | --- | --- | --- | --- |
| ADR-001 | Deliver Web first. Prefer Compose Multiplatform Web/Wasm, with a 45-minute browser-build gate and a minimal HTML/JS fallback. | A public link suits judging. The team lacks Mac/Xcode for local iOS builds. The gate limits exposure to tooling problems while preserving the Kotlin option. | Start with HTML/JS, target native first, or spend more time on Wasm before adopting a fallback. | A records toolchain versions, command, output and browser result. D records the selected path. Both UI paths use the same API. Android and iOS are future paths. |
| ADR-002 | Build a Kotlin/JVM Ktor backend and deploy the Web frontend and API to Vercel and Railway respectively. | Ktor matches the Kotlin direction. Separate deployment suits a static browser bundle and a server process. The plan records existing Vercel setup. | Co-host the browser UI and API, or use a different backend stack or hosting provider. | Deploy from `main`. Verify provider account access and quotas, build output, Railway health, the public API base URL and the deployed browser origin. |
| ADR-003 | Keep MVP search stateless and unauthenticated. | Journey searches can be served without profiles or persisted user data. Static curated places and historical artifacts can ship as files later. | Add a database and user accounts during the MVP. | Store no personal journey data by default. A feature requiring durable state or identity needs its own decision. |
| ADR-004 | Use an adapter around a Swiss transport routing API and rank its valid journeys by earliest scheduled arrival for a fixed earliest departure. Preserve provenance. | Timetable planning requires valid time-dependent connections. The deterministic rule is explainable and testable within the MVP window. | Implement timetable graph routing, optimize elapsed duration, or rank with unverified forecasts. | Validate the provider terms, limits, failure behavior, schedule fields and cancellation semantics before the live release. Use explicit `MOCK` data only for demo or tests and prefer provider-supplied labels and platforms when available. |
| ADR-005 | Use app-owned HTTP JSON contracts and separate frontend and backend DTOs for the initial slice. | The dependency stays usable from Compose/Web, the fallback UI and future clients. Provider schema changes remain inside the transport adapter. | Share a Kotlin DTO library immediately or expose provider response shapes to the browser. | Use matching JSON examples and review schema changes with the frontend, backend and integration owners. Reassess a shared Kotlin module after verifying JVM and browser compilation and resolving a concrete reuse need. |
| ADR-006 | Use `GET /health` and `GET /api/journeys` as the documented v1 baseline. Carry explicit UTC offsets. Render times in `Europe/Zurich`. | Health can be tested independently from the provider. Journey search has small read-only inputs. Offset timestamps allow correct ordering across daylight changes and midnight. | Use `POST /api/journeys/search` immediately or accept unzoned local times in the API. | A and B review v1 names, validation, nullable fields and example fixtures at kickoff. D coordinates migration of changed contracts. Deadline and preference request fields remain future work. |
| ADR-007 | Keep analytics offline. Use no prediction by default and load only a versioned, validated artifact into Kotlin when evidence supports it. | The CSV schema, coverage and labels need validation. Offline analysis keeps Python out of the journey request path. | Run a Python inference service, build prediction into the first milestone, or infer probabilities from incident counts. | C audits the data before analysis. Descriptive findings can be useful with incident-only data. Probability claims require eligible labels, coverage, chronological evaluation and calibration. |
| ADR-008 | Keep a deployable `main` and merge short changes through reviewed feature branch PRs. | Four developers can integrate vertical slices early and preserve known-good demo checkpoints. | Push directly to `main` or hold work on isolated branches until the final demo. | D coordinates checks, smoke evidence and milestone tags. Use `feature/frontend-mvp`, `feature/backend-ktor`, `feature/analytics` and `feature/integration` as requested for this repository. |

## Decisions to revisit when evidence is available

- Select a routing provider after checking real route results, permitted data use, rate limits, error cases and available fields. Record field-level support and current limits with the selection. [Backend setup](../backend/README.md)
